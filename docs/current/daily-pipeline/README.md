## 设计思路与软件层次

按业务职责划分逻辑模块，组件不等同于独立部署的服务。本系统采用表示层、业务层、数据与外部接入层描述软件结构。

| 层次 | 模块 | 功能 |
| --- | --- | --- |
| 表示层 | 看板前端 | 概览、Daily 用例、流水线触发、流水线采集、问题跟踪及处理进展展示 |
| 业务层 | Daily 用例管理 | 维护从 Nightly 挑选的 Daily 用例、标签、启用状态和用例处理标记 |
| 业务层 | 触发与调度 | 保存 Token/Cron，读取配置与处理标记，筛选本轮用例，生成参数，触发主流水线，保存触发日志和用例快照 |
| 业务层 | 流水线采集 | 关联主/子 Run，采集 Job 和用例执行结果、时间及 Issue，向自动处理模块提交新增失败 |
| 业务层 | 自动问题处理 | 后台自动定位，执行代码、版本配套、环境问题策略，记录阶段结果和时间，更新调度标记 |
| 业务层 | 问题跟踪 | 查询失败用例、Issue 正文与评论、处理进展和依赖关系，管理本地记录并支持主动关闭 Issue |
| 业务层 | 统计查询 | 聚合概览指标和图表数据 |
| 数据与外部接入层 | 数据访问组件与数据库 | 持久化配置、触发快照、Run 关联、执行结果、Issue 关联和处理任务/阶段记录 |
| 数据与外部接入层 | GitHub 接入组件 | 统一访问社区工作流、PR 和 Issues，触发与采集共用 Token 配置 |
| 数据与外部接入层 | 通知接入组件 | 调用独立通知系统并接收结果 |

自动问题处理属于看板后台。测试由 vLLM Ascend 社区流水线执行，看板负责配置、触发、采集和处理。通知系统独立于第二部分，本图仅保留其接入关系。

## 必须保持的业务约束

1. **调度读取路径**：Daily 用例管理负责保存配置；触发与调度通过数据访问层直接读取配置和处理标记，自行完成筛选，不调用用例管理来“获取可调度用例”。
2. **可执行条件**：本轮用例同时满足已选中、已启用、处理标记允许执行。禁用用例仍可在配置页面勾选；禁用用于定时执行时过滤。
3. **统一时间来源**：触发页配置 Cron；Daily 用例配置/编辑页展示由其生成的时间选项，单独修改暂不开放。时间选项不能单独表达 Cron 的日期条件，实际调度仍遵循完整 Cron。
4. **社区执行范围**：触发 `schedule_daily_test.yaml`，其中 `run-all-tests` 执行 UT 与 PR E2E 的 main/release 两套版本，Daily 路径按硬件调用 Nightly 子工作流执行配置中的 Daily 子集。保留其他 Job 的执行结果，基础设施或调度 Job 失败不能伪装为测试用例失败。
5. **触发与执行分离**：`workflow_dispatch` 受理不代表执行完成；主流水线 dispatch Job 成功也不代表子工作流测试成功。触发前保存本轮快照，后续配置修改不能改变本轮历史。
6. **Run 关联**：保留触发记录、主 Run、子 Run 的关联；界面展示最终执行结果，当前不按 attempt 单独展示。无结束时间时耗时显示为空。
7. **Issue 所属**：Issue 在 vLLM Ascend 社区维护，由社区侧首个失败增量创建并更新；看板采集关联，调度开始时不预建 Issue。
8. **幂等与调度标记**：新增失败创建后台处理任务，并及时标记处理中、禁止后续调度。重复采集同一失败不能重复创建任务或回退 PR。最终结果继续更新用例处理标记；已解决后仍需满足选中和启用条件。
9. **代码问题处理**：问题定位 → 回退 PR → 问题 PR 通知 → PR 合入 → 已解决；时间窗口内未合入进入未解决。
10. **版本配套处理**：问题定位 → 回退版本 PR → PR 合入 → 重新构建镜像 → 已解决；未合入、构建失败或超时进入未解决。
11. **环境问题处理**：按照现有业务流程，定位为环境问题后执行“标记成功”策略，不自行增加环境恢复或复测环节。
12. **查询无处理副作用**：打开处理进展页面、点击时间点、查看依赖图只读取已保存状态，不启动定位、回退或构建任务。历史测试失败结果与后续问题处理结果分别保留。
13. **Issue 状态与依赖**：Issue 依赖图直接关联该 Run 下的失败用例处理状态，不展示 Run 中间节点。图本身不触发关闭；支持主动关闭及社区其他关闭方式，实际状态以 GitHub 为准。即使 Run 采集结束，仍独立同步保留跟踪的 Issue 状态。
14. **状态展示**：GitHub 实际状态使用 `open` / `closed`；界面的 Issue 链接按已确认的 `#编号-open` / `#编号-close` 展示。处理结果展示成功、失败、执行中，与测试执行结果分开。

## 实现时需要补齐的技术契约

- 触发请求与主 Run、子 Run 的可靠关联方案需要明确；不能仅凭固定 `request_id=daily` 区分多轮运行。
- 明确子工作流输出的用例结果格式、标识和获取方式，分别处理用例失败与 Job 失败。
- 明确失败记录的幂等键、处理任务持久化与恢复、处理时间窗口及重试规则，避免重启或重复采集造成重复副作用。
- 明确 Cron 使用的时区及其与工作流触发方式的关系，保证前端时间预览和后台实际调度一致。
- Daily 子集为空时显式表达空集合，避免被社区工作流按“未提供配置”回退为默认用例。
- 当前前端 Mock 只用于交互验证；后台自动处理、GitHub 状态同步及真实关闭等能力需要按本基线实现和验证。

## 问题跟踪实现状态（2026-11-17）

新增四表：`daily_pipeline_failures`、`daily_pipeline_issues`、`daily_pipeline_process_nodes`、`daily_pipeline_process_node_executions`。迁移入口为 `database/migrations/daily_pipeline_tracking.py`，已加入标准初始化流程。

采集事务识别 test_job 失败并幂等登记；新失败替代同一对象的旧流程。Issue 独立按分钟同步，关闭后结束关联流程并解除 Daily 调度阻断。失败历史不依赖采集树级联生命周期。页面查询不启动处理。

业务层入口为 `backend/daily_pipeline/tracking.py`；持久层入口为 `backend/infrastructure/persistence/daily_pipeline_tracking.py`。节点执行器按管理员鉴权接口 `processing/nodes/{id}/start`、`processing/executions/{id}/wait`、`processing/executions/{id}/finish` 回报真实结果。定位成功必须返回 category=code/version/environment；等待 PR 提供 pr_number，等待构建提供 run_id。服务按分钟检查外部等待结果，旧流程回调被拒绝。

自动定位、生成回退 PR、通知和触发镜像重建的实际执行器尚未连接；定位节点保持 pending，不生成模拟结果或自动发起社区写操作。PR/构建监控在执行器提交真实引用后可用。处理窗口规则尚未确定，暂不保留截止时间字段及超时终止逻辑；保留 ended_at 记录实际结束时间。独立通知系统的协议也尚未确定。


### 失败来源归一化（2026-11-17）

失败表仅保存 `node_id`、Issue 关联与处理状态。名称、硬件、版本、原生 Job/Run 身份和执行时间统一保存在采集节点/主轮次，通过联表读取。迁移 `daily_pipeline_failure_source.py` 回填关联并移除旧重复列，保留失败与处理节点原有 ID。

采集节点的 `is_current` 区分当前快照和历史；新快照不再物理清理旧节点。采集记录删除改为主轮次 `deleted_at` 隐藏，并取消当前节点标记。失败来源外键禁止物理删除已引用节点，因此 rerun 和采集列表删除均不删除处理历史。调度阻断及新旧流程匹配同样联表读取执行事实。


### 故障禁用与自动恢复（2026-11-17）

用例目录 `enabled` 保留用户手动设置；`auto_disabled` 由当前仓库的未解决 Daily 失败决定。页面有效状态与调度条件均要求 enabled=true 且 auto_disabled=false。采集、新流程替代、处理成功、Issue 关闭及目录同步均在原事务内重新计算自动限制；UT/E2E 不禁用 Daily 目录项，硬件身份统一按小写匹配。同用例仍有其他未解决失败时继续禁用。

API 返回 manualEnabled、autoDisabled、processingFailureId。Daily 列表自动禁用时显示橙色“故障禁用”标签，点击进入处理进展，故障期间不允许直接打开有效状态开关。编辑标签时保留手动开关，避免把自动禁用误存为人工禁用。Issue 关闭/处理解决只清除自动限制，不覆盖用户开关。
